# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repo Is

This is the **documentation site** for the Logos project — a modular team operations platform. It is an [Astro](https://astro.build/) + [Starlight](https://starlight.astro.build/) static site containing Markdown docs and a GitHub Actions deployment pipeline. There is no application code here; the Go packages and modules are in separate repositories.

## Build and Serve

```bash
# One-time setup
npm install

# Local dev server (http://localhost:4321/logos-docs/)
npm run dev

# Production build (used in CI) -> ./dist
npm run build

# Preview the production build
npm run preview
```

`npm run build` fails on content/config errors. Always build locally before pushing.

## Deployment

Pushes to `main` trigger `.github/workflows/deploy-docs.yml`, which builds with Node 20 (`npm ci && npm run build`) and deploys the `dist/` output to GitHub Pages automatically.

## Documentation Structure

Content lives in `src/content/docs/` (English only; the site is single-locale with `defaultLocale: "root"`). Every page needs a `title` in its frontmatter. The navigation hierarchy is defined in `astro.config.mjs` under the Starlight `sidebar` config (using page `slug`s) — always update it when adding or renaming pages.

- **Foundations** — Architecture, requirements, core responsibilities, module taxonomy, full-system message flow
- **Channels** — Channel message flow and envelope contract with core
- **Contracts** — wire contracts between modules and core: AMQP envelope and routing, module lifecycle, HTTP sync (data plane), module management, module logs (live tail), minion connection schema, minion build (built; payload crypto pending), plus the "Implementing a Module" guide (checklist + the Go SDKs: `logos-golang-module-core`, with `logos-golang-channel-core` and `logos-golang-factory-core` on top, and BOB as the reference factory)

There is no ADR section: design reasoning lives in a **Design notes** section at the end of the contract page it belongs to. Contract pages state facts from the code (protocol types, module-core, channel-core, core) — check a field or limit there before documenting it. The exception is a page that opens with a `:::caution[Draft]` aside: it records an agreed design before it is built. When the code lands, check the page against it, drop the aside, and set its status in the overview's contracts table.

## Key Concepts for Editing Docs

- **Two module types**: Channel Modules (transport) and Factory Modules (build minions). Channels are plaintext-blind — they relay encrypted blobs only. Factories may optionally implement translator hooks for a custom minion language (planned, not built); these are a factory-owned implementation detail, not a separate module type. There are no dialers: a channel declares the **connection kinds** it supports, by who dials and how long the connection lasts (`reverse-call` and `reverse-persistent` built, and connection management: the hello's `conn`, `conn_update` (item 14), the `switch_connection` action; `bind-call` built too: the control link's `call`, targets (states, retries, needs editing, takeover of a session), the `rehello` item, the Dumbo channel and factory; `bind-persistent` built too: the link's `open`, target policies (on-demand, manual, always), Connect/Disconnect, idle closes (not while a task the connection carried runs), connected only once the target's minion spoke (another build's minion, or silence within the open's time, is not the minion; a quick drop is a failed open, backing off), the TCP channel and BOB's listening minion; persistent connections in general: one socket per minion connection, closed by the channel when the minion's connection ends or stops answering, a connection its first speaker's own (sessions a pivot relays are reached over it, but checked in only by their own messages), a hello naming no `conn` taken to come through the connection that carried it when only one of the build's fits, answers to pushes over any socket of the session, a closed session told over its sockets, a socket no open session uses for 2 minutes closed; lost replies: a message seen again within 10 minutes gets the reply it got (kept up to 64 KiB; core no longer dedups on the sync call's `Logos-Message-Id`), a hello again under a temporary id within 10 minutes gets the session the first opened, and core's handling of a message is its own (2 minutes, whatever the channel); a minion with no schedule is taken to keep a day's on a reverse kind; failover (the build's policy: `failover` in the build request and per connection, the schema's `failover` flag, BOB's minion) built too; `add_connection` a draft in `contracts/channel-core-connections.md`; `module-types.md` keeps the kinds' overview). How every minion-message mechanic goes on each kind, how core's messages reach a minion (one outbox, a nudge that pushes, calls or opens), and the checklist a new mechanic must answer to fit all four kinds are in `contracts/minion-messages/index.md` ("Mechanics by connection kind"): keep that table in step when a mechanic changes. Parts of it live in the protocol: the `poll` item (16, core asks a polling minion to come back sooner), the `max_tasks` item (17, both ways: how many tasks a minion runs at once, set live by core in any message until the minion says it has it; the hello's key 17; the build schema's `max_tasks` flag and the build request's `max_tasks`), the `feedback` item (18, minion → core: a warning or an error for its operators, kept with the session, unread counts on it), the `reack` item (19, core → minion: which of the tasks core thinks it runs the minion still has, asked after a claim and over each new `bind-persistent` connection; an `ack` for those it has, `unknown_task` for the rest, which core ends), core's `at` (message key 4) with `err` `stale` (7) for minions that cannot remember ids, `err`'s `ctx` (key 5, echoed), a kind's `max_message` in the connection schema (and `max_message` on build connections), a `bind-call` kind's `max_call` (how long its calls may take: core's deadline, 2 minutes when none is declared, 10 at most; a call sent is always waited for, a refused target called again only on Check now or an edit, and a call core itself could not make tried again in a minute), a `bind-persistent` kind's `max_open` (how long its opens may take, and again its minion's first word: 30 seconds when none is declared, 10 minutes at most), and commands' `kinds` in the build schema. Each kind declares its own fields in full on both sides: the channel's connection schema (`schema_version` "2", `kinds` map) and the factory's build schema (`schema_version` "3", `channels[].kinds` list); endpoints are of one kind and export as `logos.channel-endpoint.v2` with `kind`.
- **Agentless channels** (`contracts/agentless-channels.md`, built: `logos-ssh`): a `bind` kind the connection schema declares `agentless` is one whose channel acts as the minion, with nothing on the target. It changes one thing in what core does: a call or an open to such a kind carries what a minion would keep: `keys` (key 11), the keys of its id (the build's under the build id, the session's under the session id), which the channel opens core's messages and seals the minion's with, and `acting` (key 14) while the session has an acting identity a task made: that task, `{1: task id, 2: cmd, ? 3: args}` as it carried them, which the channel takes up again (the page's "The acting task"); every other channel stays plaintext-blind. Builds are sealed alike for every channel (there is no `none` suite: it was built and dropped). Core never speaks first on a persistent connection: an `open` says the id the minion speaks under (`under`, key 10). A hello's `pid` is optional (0: no process of its own). The SSH module (`logos-ssh`: an `ssh` factory and an `ssh` channel with its own minion) is the first; it serves Unix servers and Windows's OpenSSH (the page's "Windows servers": Windows paths, attributes and junctions from cmd's `dir`, the default shell stopped by a signal, the hello and drives from PowerShell, as BOB's minion has them on Windows). Its `become`/`unbecome` (the page's "Become": sudo, sudo su or su; one shell elevated a connection, shell commands typed into it in turn, the rest as the login; elevated again on each connection from core's `acting`; a become nests in the one in effect, or goes from the login when that one does not elevate; Unix only) are ordinary commands to core, which learns the identity from `identity` items. Minions share the protocol and contracts, never their workings: each keeps its own task runner.
- **Credentials** (`contracts/credentials.md`): connection and build schemas may declare `credential` / `credential_list` fields (`accept`: the credential types; not in management manifests). Core keeps ids where it keeps values and gives the module the credentials beside them (a build request's `credentials`, a link call's or open's key 12), or in a task's arg in place of the id; properties, tags, validity and comments never go. A channel's answer says its logins (key 13): core marks a credential that logged in valid and notes each on the target. The SSH channel's targets log in with them.
- **Identity** (`contracts/minion-messages/identity.md`): the `identity` item (20, minion → core) says who a session's tasks (scope 1) or one task (scope 2) run as when not the process's own (`how`: impersonation, network, become); the hello stays the process's. Core knows no command that changes it (those are the factory's): it takes a message's items in order and records each task as the session's identity when its ack came (a minion acks in the order it took the tasks, several acks a message; a task acked before a change that ran after it says its own), keeps the session's `acting`, each task's `as` and a history (process, session, task), and marks a credential an identity names valid.
- **Tunnels** (`contracts/minion-messages/tunnels.md`, released: protocol v0.36.0, BOB v0.26.0; reverse port forwards and `stop_idle`: protocol v0.37.0, BOB v0.27.0; core's fronts, `opens`, the strict open and the cap: protocol v0.38.0, BOB v0.28.0; unix sockets, named pipes, a source address and TLS: protocol v0.39.0, BOB v0.29.0; a terminal front, SOCKS5 BIND and `tunnel_ctl`: protocol v0.40.0, BOB v0.30.0; `stop_idle` core's: protocol v0.41.0, BOB v0.30.1): TCP streams the minion opens from its host, carried in messages (items 21–26: `tunnel`, `tunnel_reply`, `tunnel_data`, `tunnel_ack`, `tunnel_close`, `tunnel_datagram`; byte offsets and a window per direction, as chunks have), inside a task of a command with a tunnel action (`tunnel` and `reverse_tunnel`, released: protocol v0.38.0, BOB v0.28.0, wave 1 of the page's Future cases: the action says the direction and the front is a core param, `front`: `socks` (core's SOCKS, the default), `http` (its HTTP proxy: CONNECT, plain requests rewritten one a connection, 502/503/504/501), `forward` (to `host:to`, no handshake, its first bytes with the open); a reverse tunnel's `forward` or `socks` (reverse SOCKS: core serves SOCKS5 on each stream, user `logos` and a 24-hex password per task, CONNECT alone, its reply naming no address of core's); core adds `front`, `port`, `host`, `to`, `cap` to every tunnel command (`CommandAction.Adds`, no num, `protocol.TunnelCoreParams`); `opens` per command (`tcp`, `udp`; none: tcp alone); an open read strictly (`protocol.ReadTunnel`: an unknown key, or an unreadable open with its task and stream, answered result 7 `unsupported`); stream numbers taken a thousand at a time (`StreamBlock`), counted apart (`opened`); core's resend after its session's round trip (RFC 6298, 5 s to a minute) with its own wake, windows growing to 4 MiB (32 MiB a tunnel); the bandwidth cap, bytes a second each way, live (`setMinionTunnelCap`); wave 2, released: protocol v0.39.0, BOB v0.29.0: an open's `kind` (1 unix, 2 pipe) and `path` (keys 7, 8; `protocol.TunnelPathKind`: a pipe in `\\`), `source` (9) and `tls` (10), results 8 `not_found` and 9 `denied`, `opens` taking `unix`, `pipe`, `source`, `tls` and a target's `opens` narrowing it (BOB's Linux target: no pipes), core offering `path`, `source`, `tls` only where opened (`tunnelCommand`), BOB's pipes overlapped through `os.NewFile` (`pipe_windows.go`); `socks_proxy`, `port_forward`, `reverse_port_forward` gone, no aliases; `TunnelActions`/`IsTunnelAction` in the protocol; the minion's side the same for every front; a tunnel task holds no place in max tasks, on either side: core's slot count (`CountSlots`) and BOB's room leave them out, the session counts them apart as `runningTunnels`); core speaks SOCKS (5, 4/4a, CONNECT; no credentials: a port is as private as the network in front of it) on one of its operational ports (`OPERATIONAL_PORTS`, `OPERATIONAL_BIND`, `OPERATIONAL_ADDRESS`), and the minion only opens, relays and closes TCP. UDP ASSOCIATE built too (`tunnel_datagram`, 26, no acks: the relay is a UDP socket on the same port number, a datagram matched to its association by the tool's address, the first binding its source; `seq` taken once each, 64 back). Core paces a polling minion with `poll` (at once while tunnel items go, 250 ms with a stream open and idle, 1 s with the task and no stream); a minion with its own tunnel items checks in at once. Receivers may keep data that starts past `next` (messages crossing), senders resend unacked data after a while and probe a shut window with one byte. Core has its side: `pkg/miniontunnels`, `operational_ports`, the task's Proxy/Forward tab and the operation's Ports page (live by `operationalPortChanged`); a tunnel's streams are never stored: core holds them in memory while the task runs (every open one and the latest 1000 ended, MinionTunnel's `kept`), and the task keeps what its tunnel came to (`tunnel`: streams counted, bytes each way), its port or listener the bytes so far for a restart; BOB's minion its own (its `tunnel` command, op 15; 16 retired). **Reverse port forwards** (released: protocol v0.37.0, BOB v0.27.0; the page's "Reverse port forward"): the `reverse_tunnel` action (`bind`, `listen`, `udp` the minion's; `front`, `host`, `to`, `cap` core's alone: added by core, no `num`, never sent), the minion listening and saying where (`tunnel_listen`, item 27), its streams the minion's (`tunnel` minion → core, numbered by it; core connects to the destination, anything the operator types, and answers a `tunnel_reply` with its result alone); core keeps `minion_listeners` (no operational port), the Ports page's Minions' ports; BOB's `reverse_tunnel` (op 17). With `udp` (the action's fifth param) the minion listens for datagrams: a stream per source (a `tunnel` with `udp` naming it), core a UDP socket of the stream's own to the destination, `tunnel_datagram` both ways naming the source, a stream ending after 2 minutes idle (`protocol.TunnelUDPIdle`: the minion closes it, core's backstop a minute later). Core adds `stop_idle` to every tunnel command (`CommandAction.Adds` since protocol v0.41.0, wave 3.1; before, an optional param the factory declared, through `CommandAction.Optional`, now gone with `CoreParams`; its defaults core's: `1h` for `tunnel`, never for `reverse_tunnel`): core stops the task (a cancel with `cancelReason`) once no stream has been open that long, the clock from the minion's ack and each last stream's end (a restart starts it again); the task's tab and the Ports page say when (`stopsAt`). **Future cases** (the page's own section, partly built: the 2026-11-07 review; wave 1 released with protocol v0.38.0 and BOB v0.28.0, the rest proposed): a matrix of the cases past the three tunnels (an HTTP proxy, reverse dynamic SOCKS, a VPN front, scans, unix sockets, named pipes, a shell, ICMP, stream options, pivots both ways, one front over several minions, SOCKS5 BIND, fast and slow links, the SSH channel, pages that keep sockets, the host's HTTP stack), how each would go, and nine proposed changes, numbered: the front a core param over two actions (`tunnel`, `reverse_tunnel`), `opens` per command, result 7 `unsupported` for an open not fully understood (an exception to ignoring unknown keys), all three built; opens of more kinds (unix, pipe, process, icmp); `tunnel_ctl` for shells; ICMP datagrams; bytes with the open; stream numbers in blocks (built); resend and windows that follow the link (core's half built). The page's "In order" holds the waves 2 to 6 still to come. **Wave 3** (released: protocol v0.40.0, BOB v0.30.0; BOB's minion: a PTY from `/dev/ptmx` on Linux, a ConPTY on Windows, pipes otherwise or as the fallback, `minion/proc*.go`, `tunnel_ctl.go`): an open's `process` (kind 3: `path` the program, none the host's shell; `args` key 11, `rows`/`cols` 12, 13; the reply's `terminal`, key 7, false on pipes) and `accept` (kind 4, SOCKS5 BIND: listens, a ctl says who came, 2 minutes `TunnelAcceptWait`), result 10 `in_use`, strict reading over keys 0–13; `tunnel_ctl` (28: size, signal 1 interrupt/2 terminate/3 kill, exit before eof, an accept's host/port), reliable: numbered each way, acked by `tunnel_ack`'s `ctl` (key 5), a stream done only once its ctls are acked; `opens` gains `process`, `accept`; core's `terminal` front (`program`, `args` as one command line split by `protocol.TunnelArgs`, `rows`/`cols` 24×80 for the raw port), its raw port and its web terminal (xterm.js, a lazy chunk; `GET /api/v1/minion-tasks/{id}/terminal`, a WebSocket for an operator: binary bytes, JSON controls, close 4000 when refused; nginx's own location), the page's "Terminal" and "Controls". Keep it in step when one is agreed (a draft) or built (into the page). The SSH channel's tunnels stay an open question.
- **The sync call** (data plane) carries a minion's ciphertext as the raw HTTP body, with `Logos-Message-Id`, `Logos-Build-Id` and `Logos-Channel-Instance` headers; core answers 200 with ciphertext or 204 with nothing. There is no JSON envelope any more (`inbound/outbound.minion_message`, `encrypted_data` are gone).
- **Channel extraction** — core defines only the sync call. How a channel module extracts the build id and its ciphertext from its transport is the channel's implementation detail and out of scope for these docs.

## Markdown Authoring

- **Frontmatter**: every page must start with a `title:` (Starlight requirement).
- **Asides/callouts**: use Starlight syntax — `:::note[Title]`, `:::tip`, `:::caution`, `:::danger` — not MkDocs `!!! note`.
- **Internal links**: link to other docs with relative directory URLs, e.g. `[Architecture](../architecture/)` or with an anchor `(../architecture/#pending-decisions)`. Do not use `.md` extensions.
- **Mermaid**: fenced code blocks with the `mermaid` language are rendered at build time to inline SVG by the `astro-mermaid` integration (no client-side flash).
- **Tables, TOC, syntax highlighting**: provided out of the box by Starlight.
- **Monochrome**: the site uses Tailwind's neutral scale, like core's UI, and no other colour. `src/styles/global.css` maps Starlight's tokens (accent, grays, the aside/badge/card hues, print) and the Mermaid diagrams to it; `src/styles/code-theme.mjs` is the grayscale code theme. Asides of different kinds differ by icon (a caution or danger also gets a stronger edge), not hue.
